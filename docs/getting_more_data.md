## Why data is the bottleneck

Our training set holds only 174 distinct bugs. Getting more labeled bugs is the main way forward; more tokens or more epochs on the same bugs is not.

| Count | What it is |
| --- | --- |
| 174 | bug fixes (pull requests) from older OpenTitan cases in hwe-bench |
| 404 | buggy files in those fixes |
| 910 | examples: 404 buggy + 404 fixed + 102 bug-free windows from buggy files |
| 2,730 | labels: 3 questions per example |
| 3.99M | tokens per epoch (median 4,155 per example, longest 7,730) |

The model produces no text. The loss scores only its answers to the 3 questions, and the code is input, never a target. So the number of independent labeled decisions is what the model learns from, not the token count.

That number is smaller than 2,730. A buggy file and its fix share all but a few lines, so each pair teaches one lesson: "this change is the bug." That leaves roughly 174–404 independent lessons.

LoRA v0 learned only the base rates. It gave the majority answer everywhere, and its bug_present log loss (0.679) matched the base rate (0.681). LoRA v1 keeps each buggy/fixed pair in the same step, which uses these 174 bugs better but adds none.

## How much data other Jev-like models used

The open Jev-like models that publish numbers trained on 4,000 to 149,000 labeled examples. Most of their labels came from code or from datasets that already had them, not from a teacher model.

| --- | --- |
| Open-Jev 27B v1.1 | 148,639 |
| Kev-27B | 145,840 |
| Open-Jev 2B / 9B | 80,816 |
| Kev-9B (LoRA + pointer head on a 9B Qwen, like ours) | 30,540 (records in its 3 training stages, without replay) |
| OpenJev-RLCD paper | ~4,000 per task |
| Ours (Phase 0) | 910 |

| Model | Base | Where the data came from |
| --- | --- | --- |

| [Kev-27B](https://github.com/jaredpalmer/kev) | Qwen3.8-27B, all weights trained | Kev-9B's data plus generated long-document, tool-routing, agent-log and guardrail records, with inputs up to 32,768 tokens. |
| [Open-Jev 2B / 9B and 27B](https://github.com/Zefan-Cai/Open-Jev) | Qwen3.5 2B / 9B and a Qwen 27B, LoRA + scalar head | Mostly generated by the project's own scripts: customer cases, game and workflow scenarios, reasoning controls. Plus WANLI, a public reasoning dataset. Its first pilot used 400 records per model. |
| [OpenJev-RLCD paper](https://arxiv.org/html/2609.38850v1) | Qwen3-1.7B | MMLU-Pro and GSM8K, where the answer is known (is Qwen3-0.6B's own solution correct?). ChaosNLI, with 100 human labels per item used as a soft target. |
| [Laya](https://huggingface.co/convaiinnovations/laya) | ModernBERT-large, 421M | A "synthetic data generator"; sizes not published. Its best benchmark score comes after fine-tuning on that benchmark's own training split. |
| [Verdict](https://github.com/Heman10x-NGU/Verdict-open-jev) | ModernBERT-base, 151M | Banking intent queries; training size not stated. |
| Jev ([Turing Post](https://www.turingpost.com/p/what-is-jev-rlcd)) | not published | Synthetic data, trained with RLCD; size and generation method not published. |

What they have in common:

- **Labels mostly come from code or from the data itself.** A teacher model labels only a small share.
- **Teacher labels are filtered.** Kev kept a complaint only where two teachers agreed with the label the consumer filed.
- **Minimal pairs.** Kev generated 896 near-identical cases with opposite answers, the same idea as our buggy/fixed pairs.
- **Hard labels.** Kev used one right answer per question. The RLCD paper used soft labels only where people genuinely disagree. None used Jev's outputs.
- **Cheap training at this scale.** Kev-9B's largest stage (16,539 new records plus 10,000 replayed) took 2.6 hours on one H200.

All numbers are as the projects report them, checked 2026-10-14.

## Where we can get more labeled data

Most new labels should come from tools, as they did for Kev and Open-Jev. That means bugs we inject into clean RTL and label with an equivalence check, and assertions labeled by SymbiYosys. Real bug fixes and existing datasets add realism. The teacher (GLM3-Flash) labels only what tools can't, and only where its answers hold up.

| Source | Questions | How it's labeled | Rough yield | Cost and risk |
| --- | --- | --- | --- | --- |
| Mutants of clean modules | bug_present, category, location | Rule-based source edits: inverted condition, wrong reset value, off-by-one, swapped signal, removed check, FSM transition. An equivalence check against the original drops mutants that change nothing. | ~40k modules × 3 mutants ≈ 120k buggy + 40k clean (estimate) | CPU time for equivalence checks on the server. Mutants look less like real bugs. |
| Assertion outcomes | "Will formal checking find a violation of this assertion?" | SymbiYosys proves the assertion or finds a counterexample. Bounded-only results get softer labels; timeouts are dropped. | [CodeV-SVA](https://huggingface.co/datasets/wyt2000/CodeV-SVA-datasets) has 324K RTL + assertion pairs that were never checked | Unknown share parses with yosys-slang; solver time |
| Bugs written by the teacher | bug_present, category, location | The teacher writes a realistic bug as a patch and names its category. The equivalence check confirms the behavior changed. | Limited by our share of the GLM3-Flash endpoint, which colleagues also use (4 requests at a time) | Ask for patches, not whole files, to save output tokens |
| Real bug fixes from git history | bug_present, category, location | The fix's changed lines give the location. The teacher reads the PR text for the category. | OpenTitan has 2,594 merged "fix" PRs before 2024; hwe-bench kept 195 | Some "fixes" aren't functional bugs. Must skip the files in `test_exclusions.txt`. |
| Existing labeled datasets | all of the above, plus "does this assertion catch this bug?" | Their own labels: [rtl-augmented-v3](https://huggingface.co/datasets/architect-ubc-capstone/rtl-augmented-v3) (948 injected bugs; strip comments first), [EquivSVA](https://huggingface.co/datasets/aditigupta/EquivSVA) (360 typed mutants, 914 assertions), [HierSVA](https://huggingface.co/datasets/AnonymousHierSVA/HierSVA) (342 modules, 28 buggy variants), [VeriThoughts](https://huggingface.co/datasets/wilyub/VeriThoughtsTrainSet) (10,104 non-equivalent implementations) | ~12k items | Small sets; filter out test-family code first |
| Teacher labels | structure questions (FSM? reset style? clock domains?) and categories tools can't decide | 3–5 teacher samples, kept only where they agree, weighted by the teacher's accuracy on tool-labeled questions | Any size | Weakest labels; measure before trusting |

Clean module pools for the mutants: [MetRex](https://huggingface.co/datasets/scale-lab/MetRex) (25,868 modules), [openrtlset-permissive-verified](https://huggingface.co/datasets/theepicflyer/openrtlset-permissive-verified) (13,625), BaseJump STL and PicoRV32. The full survey is in `docs/hf_dataset_survey.md`.

Two rules apply to every source:

- **Keep pairs together.** Each mutant trains in the same step as its original, like our buggy/fixed pairs and Kev's minimal pairs.
- **Keep the tests clean.** Drop code from the test families (OpenTitan files in `test_exclusions.txt`, Ibex, CVA6/Ariane, PULPissimo, OpenPiton, OR1200, Caliptra). Remove near-duplicates with MinHash, and split by project family.

## Chip security CWEs as data

Yes, but as the label set and as recipes for making security bugs, not as training examples. MITRE's catalog has few hardware code examples, and most of them come from our test designs.

**What the catalog holds.** These counts come from the [Hardware Design view](https://cwe.mitre.org/data/definitions/1194.html) of CWE 4.20, the catalog's current version (downloaded 2026-10-14):

- **Weaknesses:** 110 hardware weaknesses. 96 have worked examples.
- **Code:** only 34 of the 110 include Verilog code: 76 code blocks in all, mostly buggy/fixed pairs.
- **Test overlap:** 25 of those 34 take their code from HACK@DAC'21 OpenPiton/Ariane or OpenTitan, the designs our two test sets use. [CWE-1234](https://cwe.mitre.org/data/definitions/1234.html), for example, quotes `reglk_wrapper.sv` from the HACK@DAC'21 OpenPiton SoC. Training on these would leak the test. The other 9 give a few dozen snippets: too few to train on, but useful as prompt examples.
- **License:** [free for any use](https://cwe.mitre.org/about/termsofuse.html) as long as copies keep MITRE's copyright notice.

**How we can use CWEs**

1. **Answer options for a CWE question.** The security benchmark uses 26 CWE IDs. The most common are CWE-1198 (22 properties), CWE-1202 (20), CWE-1262 (19) and CWE-1281 (12). CWE-1198 and CWE-1202 are catalog categories, not single weaknesses, so our options must include them as they are.
2. **Recipes for injected security bugs.** A CWE's description, mitigations and non-test examples go into a teacher prompt. The teacher injects that weakness into a clean training module and writes an assertion that should catch it. SymbiYosys confirms the assertion fails on the injected version and holds on the clean one. The CWE label is known by construction.
3. **CWE labels for rule-based mutants.** Each security mutation is mapped to a CWE (table below), so even cheap rule-based mutants carry a CWE label.
4. **Descriptions in the question.** Each option can carry its one-line CWE description, so the model reads what an option means. This may help with CWEs that have few training examples; it's worth testing, not essential.

| Bug we inject | CWE | What the formal check confirms |
| --- | --- | --- |
| Lock register still writable after lock | CWE-1231 Improper Prevention of Lock Bit Modification | Once locked, the register never changes |
| Debug or scan mode overrides the lock | CWE-1234 Hardware Internal or Debug Modes Allow Override of Locks | Entering debug mode doesn't clear the lock |
| Debug access without authentication | CWE-1191 On-Chip Debug and Test Interface With Improper Access Control | No debug grant without a passed authentication |
| Key not cleared on entering debug | CWE-1258 Exposure of Sensitive System Information Due to Uncleared Debug Information | The key register is zero one cycle after debug starts |
| Security register reset to the wrong value | CWE-1271 Uninitialized Value on Reset for Registers Holding Security Settings | After reset, the register holds its secure value |
| Register writable from a lower privilege | CWE-1262 Improper Access Control for Register Interface | A write below the required privilege leaves the register unchanged |
| Protected and open address ranges can overlap | CWE-1316 Fabric-Address Map Allows Programming of Unwarranted Overlaps of Protected and Unprotected Ranges | An address in a protected range is never granted to an unprivileged access |
| FSM can hang or reach a bad state | CWE-1245 Improper Finite State Machines (FSMs) in Hardware Logic | The FSM always leaves each state, and never enters an undefined one |

**Existing CWE-labeled RTL datasets**

- **[ReFormAI](https://dvcon-proceedings.org/wp-content/uploads/1083.pdf) (Infineon, DVCon):** 60,000 SystemVerilog designs, written by 4 LLMs from 30 problems, covering 10 CWEs. Each is labeled by Cadence Jasper with an unbounded proof, and about 60% are vulnerable. It's the right shape for us, but I found no public download, and 30 problems is little variety (median 34 lines).
- **[BugWhisperer](https://arxiv.org/html/2505.22878v1) (University of Florida, VTS 2025):** 4,000 vulnerable designs, made by having GPT-4/4o rewrite 13 vulnerabilities in the CVA6 (Ariane) core. It's [on GitHub](https://github.com/shamstarekargho/Hardware-Vulnerability-Dataset). CVA6 is a test family, and the set has no clean designs, so we can't train on it.
- **Our Hugging Face survey** found no hardware-CWE source that isn't built from the test families.

So the CWE list gives us the vocabulary and the recipes. The examples themselves come from our own injections into clean, non-test RTL, labeled by formal tools. This is Phase 5 of the plan.

## Targets and plan

The target for dataset v1 stays the plan's Phase 1 goal: about 40,000 modules from outside the test families. That is roughly 160,000 examples (each module plus ~3 mutants), mostly labeled by tools. We get there in stages, testing on real bugs after each.

**Shorter inputs make this affordable.** Our Phase 0 examples have a median of 4,155 tokens. Module-level examples of about 1,500 tokens cut training time about 3× per example. They also make a one-line bug easier to find. Times below assume v0's speed of about 5,000 tokens/s on 4 H20s.

| Stage | Examples | Tokens per epoch | Training time per epoch |
| --- | --- | --- | --- |
| Phase 0 (now) | 910 | 4.0M | ~13 min |
| First slice (Kev-9B scale) | 30,000 | ~45M | ~2.5 h |
| Dataset v1 | ~160,000 | ~240M | ~13 h |

Labeling also costs CPU time on the server: an equivalence check or a SymbiYosys run per mutant. That cost isn't measured yet; the pilot below measures it.

**Order of work**

1. **Finish the Phase 0 checks.** The formal tools (guide step 5) pass on the server, and it reaches the teacher, GLM3-Flash. Left: `teacher.py bench --concurrency 4` (step 6), which sets our teacher budget.
2. **Pilot on 1,000 modules.** Build the mutator and the equivalence-check labeling. Measure the yosys-slang parse rate, the share of mutants that change behavior, and seconds per check. Measure CodeV-SVA's parse rate on 1,000 assertions too.
3. **Switch to module-level examples** of about 1,500 tokens, so bug location chooses among the blocks of one module.
4. **Build the 30,000-example slice, train and evaluate.** This is the first real test of whether more data helps.
5. **Scale to dataset v1.** Add assertion outcomes from CodeV-SVA, bugs written by the teacher, and real fixes mined from git. Add teacher labels for structure questions only after measuring the teacher against tool labels.
6. **Phase 5 security data:** CWE-based injections, as in the CWE section above.

**How we know it worked.** Each stage is judged on the real bugs in hwe-bench's test cases, never on mutants alone. Bug_present pairs should beat 0.5, and blocks-only bug location should beat chance (0.150 / 0.359), with calibration kept. If mutants help on mutants but not on hwe-bench, we shift toward teacher-written and mined bugs.

**Leakage checks on every build**

- Drop code from the test families by name pattern and by `test_exclusions.txt`.
- Remove near-duplicates with MinHash, against the test sets as well as within training.
- Split by project family, and keep each mutant in the same split as its original.
